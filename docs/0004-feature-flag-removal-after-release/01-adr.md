# ADR-0004: account-creation フィーチャーフラグの削除

## ステータス

承認済

## 日付

2026-03-21

## 意思決定者

- プロジェクトオーナー

## コンテキストと課題

銀行システムサンプルプロジェクト（ADR-0001〜0003で段階的に構築）において、口座開設機能（`account-creation`）は安定稼働が確認され、フラグが恒久的にONの状態となっている。以下の課題に対応する必要がある：

- **未使用フラグの残存**: `account-creation` フラグは `application.yml` に `true` で定義されているが、`CreateAccountUseCase` では `FeatureFlagService.isEnabled()` によるガードチェックが実装されていない。つまり、フラグの値に関わらず口座開設機能は常に有効であり、フラグ定義自体が死コードとなっている
- **誤解を招く設定**: `application.yml` にフラグが存在することで、このフラグがコードで参照されているかのような誤解を新規参画者に与える
- **テストへの影響**: `FeatureFlagServiceImplTest` で `account-creation=true` がテストデータとして使用されており、フラグ基盤のテストに不要な依存を生んでいる
- **フラグ負債の先行例**: このフラグは他の5フラグ（`deposit`, `withdrawal`, `transaction-history`, `account-closure`, `withdrawal-fee`）の削除に先立つパイロットケースとして位置づけられる。最もリスクの低いフラグから削除プロセスを確立する
- **TBDのフラグライフサイクル**: ADR-0001で定義されたフラグのライフサイクル「導入（OFF）→ 段階的有効化（ON）→ コードクリーンアップ（フラグ削除）」の最終ステージをまだ実行していない

## 決定

「口座開設機能のフィーチャーフラグが未使用のまま `application.yml` に残存し死コードとなっている状況において、設定ファイルの正確性と保守性向上という課題に直面し、コードベースの明瞭性とフラグ削除プロセスの確立を達成するために、`account-creation` フラグ定義の削除と関連テストの修正を採用する。フラグ基盤テストのテストデータ変更に伴う一時的な修正コストを受け入れる。」

### 具体的な決定事項

1. **削除対象**: `application.yml` の `bank.features.account-creation: true` 定義を削除する
2. **テスト修正**: `FeatureFlagServiceImplTest` のテストデータから `account-creation` を除去し、他の既存フラグ（例: `withdrawal`）をON側のテストデータに置き換える
3. **ユースケース変更なし**: `CreateAccountUseCase` はそもそもフラグを参照していないため、コード変更は不要
4. **他フラグへの影響なし**: 本ADRは `account-creation` フラグのみを対象とし、他の5フラグには触れない
5. **フラグ削除プロセスの確立**: 本ADRの実施を通じて、今後のフラグ削除時に踏むべき手順（影響調査→定義削除→テスト修正→検証）をパターンとして確立する

## 検討した選択肢

### 選択肢1: フラグ定義の削除とテスト修正（採用）

`application.yml` から `account-creation` フラグ定義を削除し、関連テストを修正する。

- 良い点:
  - 死コードの除去により `application.yml` の正確性が向上する
  - 変更範囲が極めて小さい（設定ファイル1箇所 + テスト1箇所）ため、リスクが最小限
  - 今後のフラグ削除の先行事例（パイロット）として、プロセスを検証できる
  - フラグのフルライフサイクル（導入→有効化→削除）の学習素材が完成する
- 悪い点:
  - テストデータの変更により `FeatureFlagServiceImplTest` の意図が若干変わる
  - 将来 `account-creation` にフラグ制御を再導入したい場合、フラグ定義の再追加が必要
- リスク:
  - 極めて低い。ユースケースコードに変更がなく、設定値の削除のみのため、機能的な影響は発生しない

### 選択肢2: フラグ定義を残し、CreateAccountUseCase にガードチェックを追加

他のユースケース（`WithdrawUseCase` 等）と同様に、`CreateAccountUseCase` にも `isEnabled("account-creation")` のガードチェックを追加し、フラグの一貫性を確保する。

- 良い点:
  - 全ユースケースでフラグパターンが統一され、コードベースの一貫性が向上する
  - 将来 `account-creation` を無効化したい場合にフラグで即座に対応できる
  - フラグ定義とコード参照の整合性が取れる
- 悪い点:
  - 恒久的にONのフラグに対してガードチェックを追加するのは、無意味な技術的負債の新規追加に等しい
  - フラグ削除の方向性（TBDのライフサイクル原則）に逆行する
  - `CreateAccountUseCase` に不要な `FeatureFlagService` 依存が増え、テストの複雑性が増加する
- リスク:
  - 「フラグがあるから使わなければ」というフラグ負債の正当化パターンに陥る

### 選択肢3: 現状維持（フラグ定義をそのまま放置）

`application.yml` の `account-creation: true` をそのまま残す。

- 良い点:
  - 作業コストがゼロ
  - 既存テストに一切影響しない
- 悪い点:
  - 死コードが残存し続け、設定ファイルの信頼性が低下する
  - 新規参画者が「このフラグはどこで使われているのか」を調査する無駄な時間が発生する
  - フラグ削除プロセスの確立が先送りされ、他のフラグの削除も進まない
  - TBDのフラグライフサイクルが「導入→有効化」で止まり、学習素材として不完全なまま残る
- リスク:
  - フラグ負債が固定化し、「フラグは削除しないもの」という誤った文化が定着する

## 決定の結果

### 確認方法

1. **フラグ定義の削除確認**: `application.yml` に `account-creation` のエントリが存在しないことを確認する
2. **全テストスイートの通過**: `./gradlew test` で全テスト（ユニット・インテグレーション・ArchUnit）がパスすることを確認する
3. **機能の正常動作確認**: フラグ削除後も口座開設API（`POST /api/v1/accounts`）が正常に動作することを確認する（`CreateAccountUseCase` はフラグ非依存のため影響なしの証明）
4. **grep による残存確認**: `grep -r "account-creation" src/` で `account-creation` の参照が残っていないことを確認する

### 影響

- ポジティブ:
  - `application.yml` から死コードが除去され、設定ファイルの正確性が向上する
  - フラグ削除プロセスのパイロットケースとして、今後の削除作業の手順が確立される
  - TBDにおけるフラグのフルライフサイクル（導入→有効化→削除）の学習素材が完成する
- ネガティブ:
  - `FeatureFlagServiceImplTest` のテストデータ変更が必要（軽微）
  - `account-creation` をフラグで制御する柔軟性が失われる（ただし現時点でも制御されていない）

## 追加考慮事項

### ドメインモデルへの影響

- **変更なし**: `CreateAccountUseCase` は `FeatureFlagService` に依存しておらず、ユースケース層・ドメイン層への変更は一切不要。影響は `application.yml`（設定）と `FeatureFlagServiceImplTest`（テストデータ）のみに限定される

### TBD（トランクベース開発）への影響

- **フラグライフサイクルの完了**: 本ADRにより、`account-creation` フラグが「導入→有効化→削除」のフルサイクルを完了する初めてのフラグとなる
- **削除プロセスの標準化**: 本ADRの実施結果を踏まえ、残りのフラグ（`deposit`, `withdrawal`, `transaction-history`, `account-closure`, `withdrawal-fee`）の削除手順を標準化する。各フラグ削除時のチェックリスト: (1) コードでの参照箇所を特定、(2) ガードチェックの除去、(3) `application.yml` からフラグ定義を削除、(4) 関連テストの修正、(5) 全テストの通過確認
- **フラグ基盤の保持**: `FeatureFlagService` / `FeatureFlagServiceImpl` は将来の新機能フラグ導入に備えて残す

### 学習目的

- **フラグ負債（Toggle Debt）の認識**: 「定義はあるが参照されていないフラグ」という具体的なフラグ負債パターンを認識し、早期発見・削除の重要性を学ぶ
- **最小リスクからの段階的改善**: 最もリスクの低いフラグ（コード参照なし）から削除を開始することで、段階的リファクタリングの実践パターンを体験する
- **設定ファイルの衛生管理**: `application.yml` のような設定ファイルも死コード管理の対象であり、定期的な棚卸しが必要であることを学ぶ
