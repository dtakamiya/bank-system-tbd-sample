# ADR-0001: 銀行システムサンプルプロジェクトのアーキテクチャ

## ステータス

承認済

## 日付

2026-03-21

## 意思決定者

- プロジェクトオーナー（学習用サンプルの設計者）

## コンテキストと課題

トランクベース開発（TBD）の実践を学習するためのサンプルプロジェクトとして、銀行システム（口座管理ドメイン）を構築する。以下の課題に対応する必要がある：

- **ドメインの複雑性**: 銀行の口座管理は、残高整合性・取引履歴・ビジネスルールなど、ドメインロジックが豊富であり、ドメイン層の独立性が重要
- **TBDとの両立**: トランクベース開発では、未完成の機能がmainブランチに入るため、フィーチャーフラグによる制御が必須
- **学習目的の明確性**: DDD・オニオンアーキテクチャ・TBDの各概念が、コード構造から直感的に理解できる設計が求められる
- **技術スタック**: Java 17、Spring Boot 3.5、Gradle、H2データベースを使用する

## 決定

「銀行システムの口座管理ドメインをサンプルとして構築する状況において、ドメインロジックの独立性とトランクベース開発の両立という課題に直面し、保守性・テスタビリティ・学習容易性を達成するために、DDD＋オニオンアーキテクチャとフィーチャーフラグを組み合わせた構成を採用する。インフラ層の抽象化によるコード量増加と、フィーチャーフラグ管理の運用コストを受け入れる。」

### 具体的な決定事項

1. **アーキテクチャ**: DDD＋オニオンアーキテクチャ（4層構成）
2. **開発手法**: トランクベース開発＋フィーチャーフラグ
3. **技術スタック**: Java 17 / Spring Boot 3.5 / Gradle / H2
4. **ドメイン範囲**: 口座管理（口座開設・残高照会・入出金・取引履歴）

### プロジェクト構造

```
bank-system-tbd-sample/
├── src/main/java/com/example/bank/
│   ├── domain/           # ドメイン層（最内層）
│   │   ├── model/        #   エンティティ、値オブジェクト
│   │   ├── repository/   #   リポジトリインターフェース
│   │   └── service/      #   ドメインサービス
│   ├── application/      # アプリケーション層
│   │   ├── usecase/      #   ユースケース
│   │   └── dto/          #   入出力DTO
│   ├── infrastructure/   # インフラストラクチャ層（最外層）
│   │   ├── persistence/  #   リポジトリ実装、JPA Entity
│   │   ├── config/       #   Spring設定、Bean定義
│   │   └── feature/      #   フィーチャーフラグ管理
│   └── presentation/     # プレゼンテーション層
│       ├── controller/   #   REST API コントローラ
│       └── response/     #   APIレスポンス
├── src/test/java/com/example/bank/
│   ├── domain/           # ドメイン層のユニットテスト
│   ├── application/      # ユースケースのテスト
│   ├── infrastructure/   # インテグレーションテスト
│   └── presentation/     # APIテスト
└── build.gradle
```

### 依存関係ルール（オニオンアーキテクチャ）

```
presentation → application → domain ← infrastructure
                                ↑
                          依存の方向は常に内側へ
```

- `domain` 層は他の層に一切依存しない（Pure Java）
- `application` 層は `domain` 層のみに依存する
- `infrastructure` 層は `domain` 層のインターフェースを実装する
- `presentation` 層は `application` 層を通じてドメインにアクセスする

## 検討した選択肢

### 選択肢1: DDD＋オニオンアーキテクチャ（採用）

- 良い点:
  - ドメインロジックがフレームワークから完全に独立し、ユニットテストが容易
  - 依存関係の方向が明確で、学習者がアーキテクチャの意図を理解しやすい
  - インフラ層の差し替え（H2→PostgreSQL等）がドメインに影響しない
  - DDDの戦術的パターン（Entity、Value Object、Repository）を自然に適用できる
- 悪い点:
  - レイヤー間の変換コード（DTO↔ドメインモデル↔JPAエンティティ）が増える
  - シンプルなCRUDでも4層を経由するため、初学者には冗長に見える場合がある
  - リポジトリインターフェースと実装の分離により、ファイル数が増加する
- リスク:
  - 過剰設計と受け取られ、学習者が本質を見失う可能性がある（→ READMEで各層の目的を丁寧に解説して対処）

### 選択肢2: 従来型レイヤードアーキテクチャ（Controller→Service→Repository）

- 良い点:
  - Spring Bootの標準的な構成で、学習リソースが豊富
  - ファイル数が少なく、シンプルに始められる
  - 初学者にとって馴染みやすい
- 悪い点:
  - ドメインロジックがServiceクラスに散在しやすく、ドメインモデル貧血症に陥りやすい
  - インフラ層への依存が上位層に漏れやすい（Spring Data JPAのEntityがそのまま上位で使われる等）
  - DDDの実践としては不十分で、学習目的に合わない
- リスク:
  - 「TBD＋DDD」という学習目的を達成できない

### 選択肢3: ヘキサゴナルアーキテクチャ（Ports & Adapters）

- 良い点:
  - オニオンアーキテクチャと同様にドメインの独立性を確保できる
  - Port（インターフェース）とAdapter（実装）の概念が明確
  - テスタビリティが高い
- 悪い点:
  - オニオンアーキテクチャとの概念的な差が小さく、実装上の違いが限定的
  - Port/Adapterの命名規約がチームによって異なり、学習資料で混乱しやすい
  - Spring Bootとの組み合わせでは、オニオンアーキテクチャの方が実装パターンが確立されている
- リスク:
  - オニオンアーキテクチャとの違いの説明に時間を取られ、本来の学習目的（TBD）が薄れる

## 決定の結果

### 確認方法

1. **ArchUnitによる依存関係テスト**: `domain` パッケージが `infrastructure`、`presentation` パッケージに依存していないことをCIで自動検証する
2. **ドメイン層のPure Java検証**: `domain` パッケージ内にSpring Framework関連のimportが存在しないことをArchUnitで検証する
3. **フィーチャーフラグの動作テスト**: フラグのON/OFFで機能の有効・無効が切り替わることをインテグレーションテストで検証する
4. **学習容易性のレビュー基準**: 各層のパッケージに `package-info.java` を配置し、その層の責務を明記する

### 影響

- ポジティブ:
  - DDDとオニオンアーキテクチャの実践的な学習が可能
  - トランクベース開発のフィーチャーフラグ運用を体験できる
  - テストピラミッドを自然に構築できる（ドメイン層のユニットテスト→アプリケーション層のインテグレーションテスト→API層のE2Eテスト）
- ネガティブ:
  - ボイラープレートコードが増加する（DTO変換等）
  - 学習者が「なぜこんなに層が多いのか」を理解するまでの学習コストがある

## 追加考慮事項

### セキュリティ影響
- **認証・認可**: 学習用サンプルのため初期段階では省略するが、将来的にSpring Securityを追加できる構造にする
- **データ保護**: 口座情報は機密性が高いドメインだが、学習用のためダミーデータを使用する。本番想定のサンプルとしてはフィールドレベルの暗号化パターンを示す余地を残す

### 運用影響
- **可観測性**: Spring Boot Actuatorを導入し、フィーチャーフラグの状態をヘルスチェックで確認可能にする
- **スケーラビリティ**: 学習用のためスケーリングは対象外。ただしステートレスな設計を心がける
- **障害復旧**: H2インメモリDBのため永続性は対象外。学習者向けにプロファイル切替でRDB接続に変更可能な構成とする

### トランクベース開発の運用方針
- **フィーチャーフラグ**: Spring Boot の `@ConditionalOnProperty` またはカスタム実装で管理。`application.yml` でフラグを切替可能にする
- **ブランチ戦略**: mainブランチへの直接コミットまたは短命ブランチ（最大1日）のみ許可
- **CI/CD**: 全コミットでテスト実行。フィーチャーフラグON/OFF両方のテストを実施
