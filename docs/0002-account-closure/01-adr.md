# ADR-0002: 口座解約機能の追加

## ステータス

承認済

## 日付

2026-03-21

## 意思決定者

- プロジェクトオーナー

## コンテキストと課題

銀行システムサンプルプロジェクト（ADR-0001で確立されたDDD＋オニオンアーキテクチャ＋TBD構成）において、口座のライフサイクル管理を拡充する必要がある。現状では口座作成・入出金・取引履歴の機能が実装されているが、口座を解約する手段がない。以下の課題に対応する：

- **ライフサイクルの不完全性**: 口座を作成できるが閉じる手段がなく、口座のライフサイクルが不完全
- **状態管理の導入**: 現在のAccountモデルには状態（ステータス）の概念がなく、解約にはAccountへの状態遷移の導入が必要
- **残高処理**: 解約時に残高がある場合の処理方針を決定する必要がある（払い戻しとして記録）
- **TBD対応**: トランクベース開発に従い、フィーチャーフラグ `account-closure` で制御し、段階的にリリースする

## 決定

「銀行システムの口座管理ドメインにおいて、口座解約機能が存在しないという課題に直面し、ドメインモデルの完全性とTBD実践の両立を達成するために、Accountモデルへのステータス（ACTIVE/CLOSED）導入と論理削除方式による口座解約機能を採用する。既存のAccountモデルへの後方互換性のない変更と、状態管理に伴う複雑性の増加を受け入れる。」

### 具体的な決定事項

1. **Accountモデルの拡張**: `AccountStatus`（ACTIVE / CLOSED）を追加し、状態遷移を管理する
2. **解約方式**: 論理削除（CLOSEDステータスへの変更）。データは保持し、取引履歴の参照は可能
3. **残高処理**: 残高がある場合でも解約可能。解約時の残高は払い戻し（REFUND）トランザクションとして記録
4. **フィーチャーフラグ**: `account-closure` フラグで制御。フラグOFF時は解約APIが501を返す
5. **解約済み口座の制約**: CLOSED状態の口座への入出金は拒否する

## 検討した選択肢

### 選択肢1: 論理削除（ステータス変更）方式（採用）

Accountモデルに `AccountStatus` を追加し、解約時にCLOSEDに変更する。データはDB上に保持される。

- 良い点:
  - 解約後も取引履歴を参照でき、監査対応が容易
  - 誤操作時のデータ復旧が可能（ステータスをACTIVEに戻すだけ）
  - ドメインモデルで状態遷移を明示的に表現でき、DDDの学習素材として適切
  - 既存の入出金ロジックに状態チェックを追加するだけで、CLOSED口座への操作を防止できる
- 悪い点:
  - Accountモデルへの破壊的変更が必要（status フィールドの追加）
  - 既存のテストすべてでACTIVEステータスを考慮する修正が発生する
  - CLOSED口座がDB上に残り続けるため、長期的にはデータ量が増加する
- リスク:
  - 既存の入出金ユースケースでステータスチェック漏れがあると、CLOSED口座に対して操作できてしまう（→ ArchUnitまたはドメインモデル内のガード条件で防止）

### 選択肢2: 物理削除方式

解約時にAccountレコードをDBから完全に削除する。

- 良い点:
  - 実装がシンプル（deleteメソッドを追加するだけ）
  - 不要データが残らず、DB容量を圧迫しない
  - Accountモデルへの変更が最小限
- 悪い点:
  - 取引履歴が口座削除後に参照できなくなる（外部キー制約の問題）
  - 誤操作時のデータ復旧が不可能
  - 銀行ドメインとしては非現実的（法規制で記録保持が求められる）
  - DDDの状態管理パターンを学習する機会を失う
- リスク:
  - 取引履歴の孤立レコードが発生し、データ整合性が崩れる
  - 実際の銀行業務では法的に許容されない方式であり、学習目的として誤解を生む可能性がある

### 選択肢3: 現状維持（口座解約機能を追加しない）

- 良い点:
  - 既存コードへの影響がゼロ
  - 追加の複雑性が発生しない
- 悪い点:
  - 口座ライフサイクルが不完全なまま
  - 新しいフィーチャーフラグ制御パターンの学習機会を失う
  - 状態管理というDDDの重要なパターンを体験できない
- リスク:
  - プロジェクトの学習効果が限定的になる

## 決定の結果

### 確認方法

1. **ユニットテスト**: Account.close() メソッドがステータスをCLOSEDに変更し、CLOSED状態での入出金が例外をスローすることを検証
2. **フィーチャーフラグテスト**: `account-closure` フラグのON/OFFで、CloseAccountUseCaseの有効・無効が切り替わることをインテグレーションテストで検証
3. **APIテスト**: `DELETE /api/v1/accounts/{accountNumber}` がフラグON時に正常動作し、フラグOFF時に501を返すことを検証
4. **ArchUnitテスト**: 既存のアーキテクチャ依存関係ルール（domain層の独立性）が引き続きパスすることを検証
5. **状態遷移テスト**: ACTIVE→CLOSEDの遷移のみ許可され、CLOSED→ACTIVEやCLOSED→CLOSEDが拒否されることを検証

### 影響

- ポジティブ:
  - 口座のライフサイクル管理が完成し、ドメインモデルの完全性が向上する
  - AccountStatusの導入により、DDDの状態管理パターンを学習できる
  - 新しいフィーチャーフラグの追加により、TBDの実践パターンが増える
  - 払い戻しトランザクション（REFUND）により、TransactionTypeの拡張パターンを示せる
- ネガティブ:
  - 既存のAccountモデルへの破壊的変更が発生する
  - 既存テストの修正が必要（ACTIVEステータスの考慮）
  - DomainException（sealed class）に新しい例外クラスの追加が必要

## 追加考慮事項

### ドメインモデルへの影響

- **Account**: `status` フィールド（AccountStatus型）を追加。`close()` メソッドを追加
- **AccountStatus**: 新規enum（ACTIVE, CLOSED）
- **TransactionType**: `REFUND` を追加（解約時の残高払い戻し記録用）
- **DomainException**: `AccountAlreadyClosedException` を追加（sealed classのpermitsに追加）
- **既存メソッドへの影響**: `deposit()` と `withdraw()` にステータスチェックのガード条件を追加

### 運用影響

- **可観測性**: 解約操作のログ出力。フィーチャーフラグ `account-closure` の状態をActuatorで確認可能
- **データ保持**: CLOSED口座はDB上に永続的に保持。学習用サンプルのためデータパージは対象外

### TBD（トランクベース開発）への影響

- **フィーチャーフラグ**: `bank.features.account-closure` を `application.yml` に追加（初期値: false）
- **段階的リリース**: フラグOFFでmainにマージし、テスト完了後にフラグをONに変更
- **既存フラグとの整合性**: 既存のフィーチャーフラグ管理方式（`FeatureFlagService`）をそのまま踏襲
