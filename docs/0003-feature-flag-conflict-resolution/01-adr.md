# ADR-0003: 機能フラグ競合時のコード分離パターン

## ステータス

承認済

## 日付

2026-03-21

## 意思決定者

- プロジェクトオーナー

## コンテキストと課題

銀行システムサンプルプロジェクト（ADR-0001で確立されたDDD＋オニオンアーキテクチャ＋TBD構成）において、トランクベース開発の特性上、複数の機能フラグが同一ドメインモデルに影響するケースが発生している。以下の課題に対応する必要がある：

- **フラグ間の競合**: `withdrawal` フラグ（ON）による出金機能の改修（手数料計算ロジックの変更等）と、`account-closure` フラグ（OFF）による口座解約機能の新規追加（ADR-0002）が、同一の `Account.withdraw()` メソッドに影響する
- **フラグ状態の非対称性**: 片方のフラグがON、もう片方がOFFの状態でmainブランチに共存するため、フラグの組み合わせによって予期しない動作が発生する可能性がある
- **暗黙的依存関係**: 口座解約時の残高払い戻しが `Account.withdraw()` を通じて行われるが、この依存関係がフラグ間で明示的に管理されていない
- **TBDの本質的課題**: 全開発者がmainブランチに頻繁にマージするTBDでは、フラグ競合は避けられない構造的課題であり、パターンとしての解決策が必要
- **現在のフラグ状態**: `account-creation`(ON), `deposit`(ON), `withdrawal`(ON), `transaction-history`(ON), `account-closure`(OFF) の5つが `application.yml` の `bank.features.*` プロパティで管理されている

## 決定

「TBDで複数の機能フラグが同一ドメインモデルに影響する状況において、フラグの組み合わせによる予期しない動作という課題に直面し、保守性・テスタビリティ・学習容易性を達成するために、Branch by Abstraction（抽象化による分岐）パターンを採用する。インターフェース追加によるファイル数増加と、抽象化の管理コストを受け入れる。」

### 具体的な決定事項

1. **コード分離パターン**: Branch by Abstraction（抽象化による分岐）を採用し、競合する箇所にStrategy/Policyインターフェースを導入する
2. **実装方式**: `WithdrawalPolicy` インターフェースを作成し、フラグの状態に応じて `StandardWithdrawalPolicy`（現行の出金処理）と `ClosureRefundWithdrawalPolicy`（解約時の残高払い戻し用）をSpring DIで切り替える
3. **抽象化の配置**: Strategy/Policyインターフェースはapplication層に配置し、ドメイン層の `withdraw()` メソッドの純粋性を維持する
4. **フラグ依存関係の明示化**: フラグ間の依存関係をADRおよびコード上のドキュメントで明示的に管理する

## 検討した選択肢

### 選択肢1: Branch by Abstraction（抽象化による分岐）（採用）

競合する箇所にインターフェース（Strategy/Policy）を導入し、フラグによって実装を切り替える。例として `WithdrawalPolicy` インターフェースを作成し、`StandardWithdrawalPolicy`（現行）と `ClosureRefundWithdrawalPolicy`（解約払い戻し用）をSpring DIで切り替える。

- 良い点:
  - ドメインモデルの `withdraw()` がフラグ制御のif-else分岐で汚染されない
  - 各Policyが独立してユニットテスト可能であり、テスタビリティが高い
  - Open-Closed Principleに従い、新しいフラグ競合が発生しても既存コードを変更せず拡張できる
  - Martin Fowlerの「Branch by Abstraction」概念の実践例として学習価値が高い
  - フラグ削除時は該当のPolicy実装を削除するだけで済み、クリーンアップが明確
- 悪い点:
  - インターフェースと実装クラスの追加によりファイル数が増加する
  - 抽象化の粒度を間違えると、過剰設計になり本質を見失うリスクがある
  - DIコンテナの設定が複雑になり、どのPolicyが有効かの把握にinfrastructure層の確認が必要
- リスク:
  - 抽象化の粒度を間違えると、フラグ削除後に不要なインターフェースが残存する（対処: フラグのライフサイクル管理で削除タイミングを明確化）
  - 学習者にとってStrategyパターンの理解が前提知識となる（対処: READMEでパターンの目的を解説）

### 選択肢2: フラグ組み合わせマトリクスによるガード条件

各ユースケースでフラグの組み合わせを明示的にチェックし、矛盾する組み合わせを早期に検出する。例として `CloseAccountUseCase` で `withdrawal` フラグも確認し、両方の状態に応じた処理を分岐する。

- 良い点:
  - 明示的で理解しやすく、コードを読めばフラグ間の依存関係が一目瞭然
  - 既存の `FeatureFlagService` によるフラグチェックパターンの自然な延長であり、導入コストが低い
  - 新しいデザインパターンの学習が不要で、即座に実装可能
- 悪い点:
  - フラグ数の増加に伴いif-else分岐が指数的に増加し、保守が困難になる（N個のフラグで最大2^Nの組み合わせ）
  - 分岐がユースケース層に散在し、どのユースケースがどのフラグの組み合わせを考慮しているか追跡困難
  - テストケースが組み合わせ爆発により膨大になる
- リスク:
  - フラグ数が増加した場合にスケールしない。現在5フラグで32通り、10フラグでは1024通りの組み合わせとなり、網羅的なテストが現実的でなくなる
  - ガード条件の追加漏れが、本番環境での予期しない動作に直結する

### 選択肢3: 現状維持（独立フラグのまま運用）

フラグ間の依存・競合はコードレビューとテストで管理し、追加の仕組みは導入しない。

- 良い点:
  - 追加の実装が不要で、現在の開発速度を維持できる
  - アーキテクチャの複雑性が増加しない
  - フラグ数が少ない現状では十分に機能する可能性がある
- 悪い点:
  - 競合検出がコードレビューという人的プロセスに依存し、見落としリスクが高い
  - フラグ間の依存関係が暗黙知となり、新規参画者が理解困難
  - TBDにおけるフラグ競合パターンの学習機会を失う
- リスク:
  - フラグ数の増加に伴い、レビューでの見落としリスクが加速度的に増大する
  - 本番環境で予期しないフラグ組み合わせが発生した場合、障害の原因特定が困難

## 決定の結果

### 確認方法

1. **フラグ組み合わせインテグレーションテスト**: 各フラグの組み合わせ（ON/ON、ON/OFF、OFF/ON、OFF/OFF）でのシステム動作をインテグレーションテストで検証する
2. **ArchUnitによる依存関係検証**: ドメイン層が直接 `FeatureFlagService` に依存していないことをArchUnitで自動検証する
3. **DI切り替えテスト**: 抽象化（Policy/Strategy）がinfrastructure層でSpring DIにより正しく切り替わることをインテグレーションテストで検証する
4. **Policy独立性テスト**: 各Policy実装が独立してユニットテスト可能であり、フラグの状態に依存しないことを検証する

### 影響

- ポジティブ:
  - フラグ競合が構造的に解決され、予期しない動作のリスクが低減する
  - Branch by Abstractionパターンの実践例として、TBDの学習価値が大幅に向上する
  - 新しいフラグ競合が発生しても、同じパターンで対応できる再現可能な解決策となる
  - ドメインモデルの純粋性が維持され、ADR-0001で確立したオニオンアーキテクチャの原則と整合する
- ネガティブ:
  - インターフェースと実装クラスの追加によるファイル数の増加
  - Strategyパターンの理解が前提知識として必要になり、学習者の認知負荷が増加する
  - フラグ削除時にPolicy/Strategyの統合作業が発生する

## 追加考慮事項

### ドメインモデルへの影響

- **Strategyパターンの配置**: `WithdrawalPolicy` インターフェースはapplication層に配置する。ドメイン層の `Account.withdraw()` は純粋な出金ロジックのみを担い、フラグによる分岐はapplication層のユースケースが適切なPolicyを選択することで実現する
- **フラグ削除後のクリーンアップ手順**: フラグが恒久的にONになった時点で、(1) 不要なPolicy実装を削除、(2) インターフェースが単一実装のみの場合はインターフェース自体を削除してインライン化、(3) 関連するDI設定を簡素化、の3ステップで整理する

### TBD（トランクベース開発）への影響

- **フラグ間の暗黙的依存関係の文書化**: フラグが他のフラグの機能に依存する場合、`application.yml` のコメントおよび該当ADRに依存関係を明記する。例: `account-closure` は `withdrawal` 機能を前提とする
- **フラグのライフサイクル管理**: 導入（OFF）→ 段階的有効化（ON）→ コードクリーンアップ（フラグ削除）の明確なプロセスを定める。フラグ導入から削除までの目標期間を設定し、長期間OFFのまま放置されるフラグを防止する

### 学習目的

- **Branch by Abstractionの実践**: Martin Fowlerが提唱した「Branch by Abstraction」概念を、実際のコードベースで体験できる学習素材として機能する
- **TBDにおけるフラグ競合の理解**: トランクベース開発の現実的な課題（フラグ競合）とその構造的な解決策を学習者が体験できる
- **デザインパターンの適用判断**: Strategyパターンをいつ導入すべきか、過剰設計との境界をどう判断するかの実践的な判断基準を示す
